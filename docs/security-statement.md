# Security statement

Generated by `scripts/gen-security-statement.mjs` from the same code `sf evidence explain` runs. Do not edit by hand: a test regenerates it and fails on any difference.

Sources covered: `audit-trail`, `limits`, `login-history`.

## Queries

These are the same for every sink.

- `Organization` [plugin, not a collector], requires: API Enabled (every user can read their own Organization record)

  ```text
  SELECT Id FROM Organization LIMIT 1
  ```

- `Organization` [plugin, not a collector], requires: API Enabled (every user can read their own Organization record)

  ```text
  SELECT Id, Name, OrganizationType, InstanceName, IsSandbox FROM Organization LIMIT 1
  ```

- `API version list` [plugin, not a collector], requires: a valid sf CLI session (the response Date header is all that is read)

  ```text
  GET /services/data/
  ```

  When: Issued by collect on every run, to end collection windows at the earlier of the local and org clocks, and by doctor only when --target-org is passed, to report clock skew.

- `limits (API budget check)` [plugin, not a collector], requires: View Setup and Configuration

  ```text
  GET /services/data/v67.0/limits/
  ```

  When: Issued by collect, once per event source, when the windows the budget guard covers span more than 7 days: the whole plan on a first run, --since or --backfill, otherwise only the gap repair. Reads DailyApiRequests.Remaining and, below the floor, refuses those windows; the routine incremental window still runs.

- `SetupAuditTrail`, requires: View Setup and Configuration

  ```text
  SELECT Id, Action, Section, Display, CreatedDate, CreatedById, DelegateUser, CreatedByContext, CreatedByIssuer, CreatedBy.Name, CreatedBy.Username FROM SetupAuditTrail WHERE CreatedDate >= <from> AND CreatedDate < <to> ORDER BY CreatedDate ASC
  ```

- `limits`, requires: View Setup and Configuration

  ```text
  GET /services/data/v67.0/limits/
  ```

- `LoginHistory`, requires: Monitor Login History (MonitorLoginHistory) or Manage Users

  ```text
  SELECT Id, UserId, LoginTime, LoginType, LoginSubType, Status, Application, Browser, Platform, SourceIp, CountryIso, LoginGeoId, LoginUrl, NetworkId, ApiType, ApiVersion, ClientVersion, AuthenticationServiceId, CipherSuite, TlsProtocol, OptionsIsGet, OptionsIsPost, ForwardedForIp, AuthMethodReference, AuthContextClassRef FROM LoginHistory WHERE LoginTime >= <from> AND LoginTime < <to> ORDER BY LoginTime ASC, Id ASC
  ```

The audit-trail <from> and <to> are the collection window, sliced by month and narrowed on timeout.

## Sink: local

### File writes

- ./sf-evidence-archive/org_id=<org>/source=<source>/year=<yyyy>/month=<mm>/part-*.ndjson
- ./sf-evidence-archive/org_id=<org>/_chain/<seq>.manifest.json
- ./sf-evidence-archive/org_id=<org>/_chain/head.json
- ./sf-evidence-archive/archive.json
- ./sf-evidence-archive/org_id=<org>/org.json
- (local sink: plain filesystem directory)
- Write order is fixed: all records first, then the manifest, then the head pointer. An interruption can leave orphan record files; it can never leave a manifest referencing a file that does not exist.

### Network destinations

- `https://<your-org>.my.salesforce.com`
  - Purpose: SOQL SELECT and REST GET against the org you authenticated to. Read-only.
  - Credential: sf CLI session (never read, copied or stored by this plugin)

### What this plugin does not do

- No DML. This plugin never writes to your org.
  - Mechanism: A static invariant test (test/unit/invariants/invariants.test.ts, rule set ORG_WRITE_RULES) scans src/ for org-mutating calls and fails the build on any match. Run `pnpm test` on the source to re-derive it yourself.
- No telemetry, analytics or usage reporting.
  - Mechanism: Absent from the source tree, not merely disabled or opt-out. The same invariant suite's static egress scan (NETWORK_EGRESS_RULES) matches known telemetry hostnames, HTTP client imports and node:http/https usage anywhere in src/, and fails the build if any appear.
- No network destination beyond the org and the sink(s) listed above under NETWORK DESTINATIONS.
  - Mechanism: These two entries are backed by different mechanisms and should not be read as the same kind of guarantee. The org entry is singular by construction, not by iteration: every collector receives a SoqlClient and a RestClient, both constructed in wire.ts (buildClients) from the same Connection, and the Organization lookups no collector owns (listed first under QUERIES) go through that SoqlClient rather than around it. The org clock read (GET /services/data/) is issued on that same Connection directly, because the clients do not surface the response Date header — so every SOQL and REST request goes to that Connection's instance URL, and there is structurally one org destination no matter how many collectors are registered; this list does not iterate collectors to produce it. The two clients are separate objects sharing one Connection, not one client. That is backed by the egress guard's filesUsingFetch check, which separately asserts that no source file makes a direct call to the global fetch API, so a collector could not quietly open its own channel even if it tried. The sink entries, by contrast, genuinely are generated by iterating each configured sink's describe() — a registered sink cannot omit itself from this list. Neither guarantee extends to subprocess execution, which the static egress guard does not scan: a sink that shells out to a network-capable binary would not be caught by it. GitSink does shell out, to the locally installed `git` binary, but only ever runs rev-parse, add, commit, remote and log — never push; that is a source-reading fact, not something the guard enforces.
- No infrastructure is created.
  - Mechanism: Every sink verifies its target exists and refuses to create it (LocalSink.init, GitSink.init), printing the command for you to run yourself instead.
- sf evidence query (separate plugin) contacts no network destination and writes no files.
  - Mechanism: The static egress scan above does not cover DuckDB: `query` runs SQL in in-process DuckDB, which is native code, and that scan reads TypeScript source for HTTP clients and hostnames, not what a native engine does. The query plugin's own TypeScript is covered by the same kind of static egress scan, in packages/sf-evidence-query/test/unit/invariants/invariants.test.ts. Like the GitSink case above, that scan does not see subprocesses: with a git sink, `query` runs only a local `git rev-parse` through GitSink.checkReadable. What backs the claim for DuckDB is the sandbox the query plugin opens it with, tested in packages/sf-evidence-query/test/unit/duckdb/sandbox.test.ts. DuckDB settings: extension autoinstall and autoload are off, and INSTALL and LOAD are refused; file access is limited to the chain-covered record files (`allowed_paths` with `enable_external_access=false`); spilling is disabled; configuration is locked before user SQL runs. This plugin's guard (guard.ts), a check over DuckDB's own parse tree: only single SELECT statements run, checked by statement type and by parse tree, so COPY TO and SET are refused by the statement guard, with the lock and the external-access settings backing that up; table functions are limited to an allowlist of read-only table functions plus DuckDB's `duckdb_*` catalog functions, and `write_log` and `setseed` are refused. The settings are DuckDB's own enforcement; the statement and function checks are this plugin's guard over DuckDB's own parse tree. Both are exercised by those tests; neither is a source-scan guarantee. This assertion is always shown, because `explain` runs in this plugin and does not know whether the query plugin is installed.
